# Limitations

Where the engine behaves differently from Excel, and what it does not do.

- **Spilling.** Of two independent arrays over the same cell, the engine always lets the lower one spill; Excel's choice varies between runs (`docs/spill.md`). An array whose size depends on a random draw spills according to the engine's clock, whereas Excel returns `#SPILL!` when the size changes between its calculation passes (for most of ten such arrays in one workbook, and for none when there is only one). A cycle through a spill range stops its cells like any cycle ([Circular references](cycles.md)). There is no `LAMBDA` (nor `MAP`, `REDUCE` or the other functions built on it).
- **Content Security Policy.** Only `execution: 'eval'` uses `new Function`: in a browser with a CSP that does not allow `'unsafe-eval'`, `compute` and `createSession` in that mode throw an `EvalError` saying so. The default `closures` mode generates no code and works under such a policy.
- **Known differences from Excel:**
  - `XLOOKUP` and `XMATCH` parse the patterns of match mode 3 (regular expressions) with JavaScript's syntax, whereas Excel uses PCRE2's: a leading `(?i)` is accepted, and constructs specific to PCRE (possessive quantifiers, `\A`, recursion) are `#VALUE!`. Excel for Windows 16.0.20430 has no match mode 3 and returns `#VALUE!`; the engine follows Excel for Mac 16.114. A pattern of match mode 3 is tested by one native regular expression call per value, so `timeoutMs` and the signal are not checked inside it: a pattern that backtracks heavily over a long text (`(a+)+$`) holds the thread until the call ends; in a pool, `hardTimeoutMs` ends it.
  - Text order for `<`, `>` and sorting uses `Intl.Collator` with the en-US order in both locales (case-insensitive, accent-sensitive, Latin before Cyrillic, as Excel for Windows sorts), which may differ from Excel for some characters; without `Intl` it falls back to comparing lowercased code units.
  - Excel for Mac sorts Cyrillic before Latin in ru-RU (`"a"<"а"` is FALSE there); the engine sorts Latin first, as Excel for Windows does in every locale, in comparisons, criteria, lookups and SORT.
  - Excel for Mac writes month names in ru-RU in lowercase (`TEXT` with `ММММ`, `МММММ` or `[$-419]mmmm`, and cells: `январь`, `я`); the engine capitalizes them, as Excel for Windows does (`Январь`, `Я`).
  - Excel for Mac writes the short month names of ru-RU (`МММ`) as `февр`, `март`, `июнь`, `июль`, `сент`, `нояб`; the engine uses three letters, as Excel for Windows does (`фев`, `мар`, `июн`, `июл`, `сен`, `ноя`).
  - A second decimal separator among the decimals of a number format (`#,##0,00` in ru-RU) is a literal between digits; Excel displays one digit fewer before it for some numbers (`TEXT(-0.5,"#,##0,00")` is `-,50,00` in Excel and `-,500,00` here).
  - `CHAR` and `CODE` take codes 128–255 from the Windows code page of the workbook's locale (Windows-1252 in en-US, Windows-1251 in ru-RU), as Excel for Windows does; Excel for Mac uses Mac Roman and Mac Cyrillic (`CHAR(200)` is `È` here and `»` in Excel for Mac en-US, and `CODE("Ж")` in ru-RU is 198 here and 134 there).
  - `CODE` of a character outside the code page of the workbook's locale is 63 (`?`), as in Excel for Windows; Excel for Mac returns 95 (`_`): `CODE("中")`, and `CODE("Ж")` in en-US.
  - When the result of `RATE` is exactly 0, it returns 0 or a value within 1e-10 of it; Excel returns its own rounding noise of up to about 2e-9, or, from some guesses, `#NUM!`.
  - `GAMMA.INV`, `CHISQ.INV`, `CHISQ.INV.RT` (and `GAMMAINV`, `CHIINV`) return the quantile where Excel's iteration fails with `#NUM!`: shapes from about 5·10^9 (10^10 degrees of freedom), and probabilities near 1 with shapes under 0.03; Excel's own `GAMMA.DIST` at the engine's result gives back the probability.
  - `BINOM.INV` where alpha exactly equals the probability of no success, (1 − p)^n: Excel decides by its own rounding of that power, the engine by exp(n·ln(1 − p)); they differ on `BINOM.INV(3,0.25,0.421875)`, which is 0 in Excel and 1 here.
  - A number that Excel calculates with a different algorithm can differ from the engine's in the 15th significant digit, within the tests' relative tolerance of 1e-9; converted to text (`&`, `TEXTJOIN`), the last digit then differs (`TEXTJOIN(";",FALSE,BESSELK(10,3))` is `2.72527006358477E-05` in Excel and `2.72527006358476E-05` here).
  - `LINEST` with a constant x variable besides the intercept: both give it a coefficient of 0 and the same fit, but Excel's statistics count it as a variable in a way the engine does not reproduce (`LINEST({1;2;3;5},{1,1,2;2,1,4;3,1,6;4,1,8},TRUE,TRUE)`: 1 degree of freedom in Excel and 2 here, and the F statistic and the intercept's standard error differ).
  - `FTEST` of a sample with itself is 1 − 3·2^-53 in Excel and 1 − 2^-52 here: the last bits of a number Excel calculates with a different algorithm can differ, which shows only when the difference is magnified (`(1-FTEST(A1:A8,A1:A8))*2^52` is 1.5 in Excel and 1 here).
  - A LET name that looks like an R1C1 row or column reference (`R2`, `C5`, `RC5`) or a boolean (`TRUE`): an xlsx file writes LET names with the prefix `_xlpm.`, so Excel loads `LET(_xlpm.TRUE,1,_xlpm.TRUE)` (1); formula text has no prefix, and there Excel rejects such a word as a LET name, as the engine does (`LET(R2,1,R2)` typed), while it otherwise accepts a cell address (`LET(A1,1,A1)` is 1).
  - A spilled array that an edit pulls into a circular reference keeps only its first value here and no longer spills, since `held` is a single value per cell; Excel for Windows keeps its entire spill as it was (the workbook set `cycles-held`, `docs/cycles.md`). Excel for Mac shows a warning dialog when opening a workbook with a circular reference, so cycles without iterative calculation were tested in Excel for Windows only.
  - Iterative calculation starts from 0 on every calculation. Excel starts a workbook it opens from the values the file stores (empty text where it stores none), and continues from the values it holds on every recalculation and edit. A cycle that converges differs from Excel's within the maximum change, and one that does not, such as a counter, keeps counting in Excel.
  - Excel's AutoCorrect extends a table when a value is typed immediately below or to the right of it, and fills a calculated column when a formula is typed into an empty column of a table; `setCells` changes only the cells typed into ([docs/tables.md](tables.md)). Formulas pasted into part of a calculated column fill the entire column in Excel too; `copyRange` pastes only the cells.
  - A table renamed to a name Excel does not accept, or to an existing defined name: Excel's object model adjusts the name to one it accepts (`AB12_`, `_1Ставка`, `_?Продажи`, `Rate_1`, `СТАВКА_1`), while its Name Box rejects it; `renameTable` rejects it with `table_name`.
  - Excel ru-RU accepts TRUE and FALSE as defined names, and Excel for Windows ru-RU as a table name; the engine stores formulas in en-US syntax, where these are the booleans, and rejects them in every locale. Excel for Mac ru-RU keeps a table named `ИСТИНА` or `ЛОЖЬ`, which Excel for Windows and the engine reject, as both versions of Excel reject such a defined name.
  - A typed formula longer than 255 characters (one using a name of 255 letters) was not tested in Excel for Mac, whose AppleScript truncates what it sets to 255 characters; Excel for Windows calculates it as the engine does.
  - Excel parses text typed into a cell as a number, a date or a boolean where it can (`2025-01-31` in ru-RU is a date); `setCells` takes a value as given, so a header cell typed this way names its column `2025-01-31` here and `31.01.2025` in Excel ru-RU. `setCellText` parses typed text as Excel does, and `parseEntry` returns the value Excel would produce, without a session.
  - `parseEntry` parses English function names and TRUE in a formula typed in ru-RU as `toInvariant` does, as the functions and the boolean, whereas Excel ru-RU treats them as unknown names (`=TODAY()` evaluates to `#ИМЯ?` there).
  - `parseEntry` has no workbook: a typed formula that refers to a cell with a date format (`=C2+1`) gets that format in Excel and none here; a typed `#GETTING_DATA` is an error in Excel and text here; an unknown name typed in a different case than earlier in the workbook (`=Foo*2` after `=foo`) is written in its first case in Excel and as typed here; and typed on the keyboard, `+5%+1` gets a percentage format and `+-+5` becomes the formula `+-5` in Excel ([docs/entry.md](entry.md#known-differences)).
  - A cell address used as a LET name and again after the LET in the same formula: Excel parses the later one as a defined name, so `=LET(IW1,5,IW1)+IW1` is `#NAME?` there and 5 here, where it is the cell.
  - Excel's formula bar keeps an apostrophe the user typed before text that did not need one (`'abc`, `'TRUE` in ru-RU); a workbook stores no such marker, and `entryText` adds the apostrophe only before text that would otherwise be parsed as something else. Excel for Mac's formula bar writes a ru-RU time with a leading zero (`01:30:00`); `entryText` writes it without one, following Excel for Windows's regional data ([docs/entry.md](entry.md#known-differences)).
  - `parseClipboard` handles quoted control characters, but plain text can encode two different grids the same way; an exact round trip needs another clipboard format or rows carried separately ([Copying plain text](entry.md#copying-plain-text)).
  - Excel's Fill Right and fill handle shift the column of a structured reference (`SUM(Sales[Qty])` filled right becomes `SUM(Sales[Price])`); `copyRange`, like copy and paste, keeps it.
  - When Excel formats a row across a formatted column (or a column across a row), it gives the cells where they cross both formats merged field by field: a bold row across a filled column makes them bold and filled. A workbook style is a single unit, and `setLayout` sets only the row's or column's own style, so the workbook displays such a cell with the row's style, bold without the fill ([docs/xlsx.md](xlsx.md#lines-excel-formats)).
  - `VAR`, `STDEV`, `DEVSQ`, `CORREL`, `RSQ`, `SLOPE`, `STEYX` and related functions, including the database ones, are calculated here from exact sums; Excel calculates them in double precision around a mean computed by plain summation, and where the spread is small relative to the mean, or the residual relative to the variation, it loses the digits of the result: for 10,000 values 1E12 + 0, 0.01, 0.02, `VAR.P` is 1.598E-04 in Excel and 6.680E-05 here, the exact value; `CORREL` of them with their steps 0, 1, 2 is 0.647 in Excel and 1 here; and `STEYX` of 1, 2.00000001, 3 on 1, 2, 3 is 0 in Excel and 8.16E-09 here.
  - Where the squares or products of the values fall outside the range of doubles, Excel returns what is left of them and the engine the exact result: the squares of 1E-200 and 2E-200 are 0 in Excel, so `STDEV.P` of them is 0 (5E-201 here, within the tests' tolerance), and `CORREL` with 1, 2 and `SLOPE` of 1, 2 on them are `#DIV/0!` (1 and 1E+200 here); a sum or a product beyond 1.8E+308 is `#NUM!` in Excel even where the result fits (`AVERAGE` of 1E+308 three times and its variance 0, and the covariance of 1E+308, −1E+308, 1E-200 with 0, 0, 1E+308, which is 2.2E+107 here).
  - `LINEST` and `TREND` over y far from 0 relative to its spread return Excel's coefficients, but Excel's intercept and regression sum of squares follow the mean it computes by plain summation: for 10,000 values 1E12 + 0, 0.01, 0.02 on their steps 0, 1, 2, the slope is 0.0100098 in both (0.010009765625 exactly), the intercept is 1E12 − 0.0096 in Excel and 1E12 here, and the regression sum of squares is 1.598 in Excel and 0.668 here (the exact value, `DEVSQ` of the values), so `TREND` at step 3 is 1E12 + 0.0204 in Excel and 1E12 + 0.0300 here.
  - `GROWTH` far from 0 in x is `#NUM!` in Excel even where the fitted value fits in a double: for 100·1.1^k rounded to cents on x = 1E10 + k, k = 0…11, the value at 1E10 + 12 is 313.84 here, where b·m^x has the b of `LOGEST` equal to 0 and m^x beyond the largest double.
  - `LOOKUP` counts among its references every cell it may read, as far as its lookup array extends, whatever value it looks up: a formula among them, the `LOOKUP` itself included, is calculated first, and a `LOOKUP` within that range is a cycle here and is not calculated (it keeps its value, 0 in a freshly calculated workbook), whereas Excel, which follows the cells `LOOKUP` actually reads, calculates it (`E10` = `LOOKUP(5,A1:A6,B10:D10)` reads `F10` in Excel and keeps 0 here, since `E10` lies within `B10:G10`; the same applies next to a spill that could not spill, and to the right of a rectangle from which `INDEX` takes a column).
  - `SUMIF` and `AVERAGEIF` count among their references the sum range resized to the criteria range, which is what they read: a formula inside it, the `SUMIF` itself included (`B2` = `SUMIF(C1:C3,"",B1)` sums `B1:B3`), or one there that reads the `SUMIF`, is a cycle here and keeps its value, 0 in a freshly calculated workbook. Excel's answer for these layouts is not recorded yet; the set `sumif-own-held` holds the engine's prediction.
  - A cell's displayed text is written from its value as the result gives it, to 15 significant digits, whereas Excel writes a date and a time from the full number: a moment a few millionths of a second from a half second can display a different second or day (`45688.99999421295` displays `31 23:59:59` in Excel with `d h:mm:ss` and `1 0:00:00` here); `TEXT` and `displayValue` of the value produce Excel's text.
  - Excel for Mac reads the long s (`ſ`) as `s`: `falſe` is FALSE in a formula, both typed and as text (`IF("falſe",1,2)` is 2), `=ſum(1,2)` typed is `SUM`, and `ſ` matches the name `S` (a LET name, a defined name, a table, a sheet); the engine follows Excel for Windows, where `ſ` is a separate letter (`falſe` is a name, so `#NAME?`, and the text `"falſe"` is not a boolean).
  - Excel compares sheet names letter by letter, so it accepts a sheet named `ß` next to one named `SS` (and `ﬁ` next to `FI`), and reads a typed function name with the dotted `İ` as `I` (`=İF(TRUE,1,2)` is `IF`; Excel for Windows also treats the dotless `ı` this way); the engine compares sheets the same way as defined names and tables, where `ß` is `SS`, and rejects the second sheet, and reads a function name letter by letter, as Excel reads one in a file (`#NAME?`).
  - `findCells` with Excel's Find options finds nothing for an empty query or `~` alone, whereas Excel's Find finds empty cells; it searches only a single-cell range, whereas `Range.Find` searches the whole sheet from the next cell; and searching by columns on a filtered sheet, it returns the first column of the first block once per wrap, whereas Excel's `FindNext`, wrapping around the whole sheet, skips it ([docs/live-books.md](live-books.md#known-differences)).
  - `replaceInCells` keeps text that looks like a number as text, as Excel keeps text typed after an apostrophe, whereas Excel's Replace turns such text without the prefix character (from a file) into a number; the workbook stores no apostrophe marker. It replaces only in a single-cell range, whereas `Range.Replace` replaces in the whole sheet ([docs/live-books.md](live-books.md#known-differences)).
  - Outlines: Excel re-evaluates the collapsed markers only for the groups whose rows change, so a summary row shown manually after being hidden along with its group stays without a marker, whereas the engine marks every summary row of an entirely hidden group, as Excel interprets a file; and columns grouped in a span of several columns reaching XFD, which Excel's level buttons leave unchanged and its Ungroup rejects, are treated like other columns ([docs/outline.md](outline.md#known-differences)).
  - `WEEKNUM` with an invalid return type is `#NUM!`, as Excel returns when it stands alone; inside one generated workbook of the random check, Excel 16.113 returned a number for `DAY(WEEKNUM(40977,1E+3)<>2.5)` (1, in two runs).
- **Displayed text.** Widths are those of Excel for Mac with the default font, Calibri 11; a cell's own font, indent, wrapping and rotation are not taken into account, characters other than Latin, Cyrillic, digits and common symbols count as a digit, and Excel for Windows lays out text at different widths, so near the edge of a column it can show `#` where the engine shows the number, or the other way round. AutoFit and the widths set by typing are Excel for Mac's: Excel for Windows fits columns to its pixels, at widths that differ from the Mac's in most columns; the Mac shows its own short date (`3/15/26`) and ru-RU month names (`март`) where the engine follows Windows; and text outside ASCII is fitted by the advance widths of Carlito, a font metrically compatible with Calibri, which differ from Excel's by a point on some long runs. Locale tags other than `[$-409]`, `[$-419]`, `[$-F800]` and `[$-F400]` (and `[$-x-sysdate]`, `[$-x-systime]`), calendars other than `B1` and `B2`, and numeral systems (`[DBNum1]`) are not supported. [docs/formats.md](formats.md) has the details.
- **The ribbon's Number Format box.** `numberFormatCategory` and `numberFormatChoices` follow Excel 16.113 for Mac in en-US and Excel 16.0 for Windows in ru-RU. Excel for Mac in ru-RU names nearly every code `(все форматы)`, as it compares the code, stored in en-US syntax, with its formats written in Russian syntax: in 100 of its 368 cells it shows `(все форматы)` where the function, like Excel for Windows, names a category. Excel for Windows names a date or time with `;@` from the lists of its Format Cells dialog (in ru-RU `[$-419]d mmm;@` is Дата, `d mmm;@` none, and `dd/mm/yy h:mm;@` Время); the function names every such code by its letters, as those codes come from such lists. Excel for Mac also names the category of a format its list applied by the list's state, and its Short Date, Long Date and Time items were not the same in two sessions on the same day; `numberFormatChoices` returns those of the first session (built-in 14, the system's long date and long time). The code `m/d/yyyy` is the short date in en-US here, as built-in 14 displays with it (the code of Excel for Windows); Excel for Mac, whose short date is `m/d/yy`, calls it Custom. Excel for Windows in en-US was not tested.
- **Syntax.** Stored formulas use English function names and separators (no `;` or decimal commas; text typed in another language goes through `toInvariant`), and no R1C1 references. A reference to another workbook needs its link in `externalBooks` (no new link is created); a reference across sheets of another workbook (`[1]Jan:Mar!A1`) and a spill reference into one are rejected. Functions outside the whitelist (`INDIRECT`, `OFFSET`, `LAMBDA`, …) return `#NAME?`.
- **Row heights.** Heights are Excel for Mac's for Calibri; a cell in another font is fitted as Calibri of its size (Arial 16 gets 21 points here and 20 in Excel), and Excel for Windows fits rows to its pixels (a line of Calibri 11 is 15 points, wrapped or not). Excel keeps every row whose height was not set manually at its fitted height, when opening a file and after any edit; the engine fits a row on AutoFit and when wrapping text is typed into it, but not when a file opens or a font changes. A formula typed or pasted over several lines keeps its line breaks in Excel's text, but not in the engine's canonical text ([docs/formats.md](formats.md#fitting-rows)).
- **Links to other workbooks.** A reference to a closed workbook is displayed with the path its link stores (`'../data/[Book3.xlsx]Sheet1'!A1`), whereas Excel displays the absolute path it resolves from the folder of the opened file. Only entering or pasting a formula with a link marks the link (`refreshError`), as verified; whether moving one or undoing does was not verified. On a marked sheet, an entire column or row is read only to one row and column beyond the stored values, so a count over it (`COUNTA`) counts one `#REF!` where Excel counts every cell missing from the values. [docs/links.md](links.md#known-differences) has the rest.
- **Structure operations and styles.** Copying entire rows or columns onto part of a merged area is rejected, whereas Excel pastes them. Styles, notes, hyperlinks, frozen panes, data validation rules and outlines are kept and moved, not evaluated: `compute` does not return them, while `Session.getCells` and `Session.getValidation` do. A hyperlink's location is not rewritten when its sheet is renamed or rows move, just as Excel leaves it. Deleting a sheet leaves a reference to one of its own names as written (`'S'!loc`, `#REF!`), whereas Excel writes the workbook's file name in its place (`'book.xlsx'!loc`) and keeps the name as a workbook name over `#REF!`; the values are `#REF!` in both.
- **Output precision.** Values in the result and in the hash are rounded to 15 significant digits, as Excel displays them; internally, calculation keeps full double precision.
- **Conditional formats.** Their effect is returned only by `Session.getCells` and `getViewport`: edits do not list the cells whose appearance changed, but return the rules' ranges as `repaint`, so a host can read its viewport again where it overlaps them. A data bar's length and an icon follow Excel's documented rules, which no object model exposes, so they were not verified; the borders, underline and strikethrough of a rule's style are kept for a host to draw. After rows are deleted, Excel moved one rule whose reference the deletion lost after the others, whereas the engine keeps its position; Excel drops the lengths of an Excel 2010 data bar other than 0 and 100 ([docs/conditional-formats.md](conditional-formats.md)).
- **Data validation.** What a dropdown displays and what picking an item enters were not verified, as no object model exposes them; a list's items are checked by which values Excel accepts. A list item containing a comma, typed in ru-RU, is read as split at the comma. [docs/validation.md](validation.md#known-differences) has the rest.
- **xlsx.** A file's pictures, charts and pivot tables are not read, and each is reported in `issues`. An error stored as a cell's value that a formula cannot express (`#CALC!`, `#GETTING_DATA`, stored as a rich value) is left out of the workbook and reported (`errorValue`), so `ERROR.TYPE` of that cell is `#N/A` where Excel returns the error's number (14 for `#CALC!`, a cell of IronCalc's `ERROR.TYPE.xlsx`). A comment thread is read and written as a note, without its dates and state; split panes that are not frozen are not read. Of a filter, the workbook keeps only the filter mode: an AutoFilter's range and criteria are reported, and a filtered sheet is written with criteria that every row satisfies. Legacy formulas are read as the dynamic formulas Excel 365 displays for them, with `@` where a single value of a range is used. Every formula is written as a dynamic array formula, which Excel 2019 and older display as an array formula. The East Asian date formats 50 to 58 are read as the code Excel for Mac en-US displays for them, `m/d/yy`, whereas Excel for Windows displays its short date in each locale. A gradient fill is read as no fill, and so are a conditional format fill that removes the cell's own fill (`patternType="none"`) and a solid fill without a color; each is reported. [docs/xlsx.md](xlsx.md) has the full list.
