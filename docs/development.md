# Development

The commands, the tests, and how the rules were checked against Excel.

```sh
npm ci
npm run typecheck
npm test                # build, then all tests against src: first all but the timed ones, then those one at a time
npm run test:dist       # build, then all tests against the built dist, in the same two runs
npm run test:oracle     # recalculate the LibreOffice answers with soffice and check them
npm run check:package   # build, then publint and attw on the packed tarball
npm run pack:release    # build, then the tarball in release/
FORMULA_BENCH=1 npx vitest run test/budgets.test.ts   # budgets on the full synthetic book
```

Tests that check how long something takes (a slice of a calculation, a deadline, a budget, the time of a drag or of `getEnd`) are in the vitest project `timed` of `vitest.config.ts`: `npm test` runs them after all the others, one file at a time, so that the load of the full suite does not make them fail. `npx vitest run <file>` runs one file in its project, timed or not.

The tests cover the whitelist against Excel's results on the coverage run's cases (`test/excel.test.ts`) and on the probes (`test/excel-probes.test.ts`); the argument layer rule by rule; the semantics cases against Excel's documentation and the stored LibreOffice results (`test/oracle/libreoffice.json`, refreshed by `npm run test:oracle`, which needs LibreOffice's `soffice` on `PATH`; the regular tests need no office suite); determinism (shuffled input, a child process, three time zones, cents over 3,400 amounts); references, errors, volatile functions, parsing and the canonical form; sessions (200 random edits against full calculations) and `explain`; structure operations against Excel's results in `test/excel/struct/`, on the synthetic workbook and on seeded workbooks; budgets; SHA-256 against test vectors and `node:crypto`; a browser bundle run in an empty JavaScript context and with code generation disabled; the two execution modes against each other on every test workbook and over 200 session edits, with the closures mode under disabled code generation; calculation in slices and in threads against the synchronous engine, lost threads and restored sessions, and the pool on Web Workers in headless Chromium, Firefox and WebKit (through `playwright-core`; each is skipped where its engine is not found, and `CHROME_PATH` points to a Chromium); and the published package (exports, tarball contents, a consumer importing it by name). The code blocks of the README run as a test too.

The Excel results the tests compare against are stored in `test/excel/`, so the tests need no Excel: the coverage run's cases and Excel columns in `coverage/`, the case sets in `cases/` (`cases/ru-RU/` for the sets calculated in ru-RU), the probes in `probes.json`, structure operations in `struct/`, spilling in `spill/`, Excel's ru-RU formula text in `locale/`, and the files Excel saved for the xlsx subpath in `xlsx/`. They are recalculated only with Excel for Mac, by a step of `npx tsx bench/coverage/run.ts`: `excel en` and `excel ru` for the coverage run, `probes` for the probes, `probes <set>` and `probes <set> ru` for a case set, `struct <set>`, `spill <set>`, `xlsx <step>`, `entry <set>` for typed text, and `cond <set>` for conditional formats; `npx tsx bench/locale/snapshot.ts ru` collects Excel's ru-RU formula text. A run keeps the stored results of unchanged cases and calculates the new and changed ones. `bench/coverage/README.md` describes the layout, the steps and the rules for driving Excel. Excel for Windows's results for the same workbooks are in `test/excel/win/`, calculated by `npx tsx bench/windows/run.ts` on a Windows machine over SSH (`bench/windows/README.md`).

Functions live in `src/functions/<category>.ts` (`math`, `statistical`, `logical`, `information`, `text`, `date`, `financial`, `lookup`, `engineering`, `database`; old names such as `NORMDIST` sit next to their modern versions), each file with its own registry, with a large category assembled from `src/functions/<category>/`; `src/functions.ts` assembles them. A function declares the kinds of its arguments (`args: 'n i?'`, see `src/args.ts`), and the shared argument layer coerces them, so an implementation receives numbers, text, lists or grids and never repeats the coercion rules. Ported code keeps its attribution in the file header. A function is added to its registry when `test/excel.test.ts` passes for it; the coverage run (`bench/coverage`, `docs/coverage-formulajs.md`) lists the cases and the classes of the remaining formula.js functions.

## How the rules were checked

The measurements behind each guide's "Checked against Excel" section: the harness steps, the sets, what each predicted set showed, and what its misses changed.

### Array operations in formulas

From [Array operations in formulas](arrays-incell.md).

The `arrays` case set (`bench/coverage/sets/arrays.ts`) is calculated in Excel as dynamic array formulas. The harness writes each formula the way Excel 365 saves one: `<c cm="1"><f t="array" ref="A1">…</f>`, plus `xl/metadata.xml` with the `XLDAPR` metadata and `dynamicArrayProperties fDynamic="1"`. Without that metadata, Excel reads a formula as a legacy one, with implicit intersection: `SUM(IF(D!B1:B8>0,D!B1:B8))` is 114.75 as a legacy formula and 118.25 as a dynamic one. The `_xlfn._xlws.` prefixes only name newer functions and do not make a formula dynamic.

A case whose result is an array is checked through a wrapper that returns a single value (SUM, INDEX, ROWS, COLUMNS, COUNTA, CONCAT, TEXTJOIN), or directly where both Excel and the engine return `#SPILL!` because every neighbor of the case is occupied.

All case sets of the library are calculated as dynamic array formulas, so the whole acceptance follows Excel 365.

The `known-held` set (37 cases) was predicted before Excel calculated it, to check rules derived from a few results of the random check: `SORTBY` with an array of sort orders, `LOOKUP` beyond the end of a shorter result, `IFS` with a text condition under `ROWS`, `TYPE` and `VSTACK`, and `SWITCH`, `IF` and `CHOOSE` alongside it. Excel for Mac and Excel for Windows returned the same 37 results, and 26 came out as predicted. The 11 misses are now the engine's rules: `SORTBY` returns results by position rather than element-wise (6), and `LOOKUP` reads a one-cell result as a row, continues reading with a calculated lookup array, and reads a blank beyond the end of the sheet (5). All 11 `IFS` cases came out as predicted.

The `lookup-held` set (19 cases) was predicted the same way for what `known-held` left open: `SORTBY` with two sort orders of the same shape, valid orders over a by-array of a different size, an order with one value next to one with two, and `LOOKUP` beyond the sheet's last column and row and beyond a reference returned by a function. Both versions of Excel returned the same results, and 10 came out as predicted. The 9 misses, and 14 cases tested after them (the `lookup-rules` set), are now the engine's rules: `SORTBY` returns `#VALUE!` after the first position that sorts when it has more than one by-array, a by-array of a different size gives its error at every position, the first position that sorts need not be the first one, and beyond a shorter order the position is `#N/A`; `LOOKUP` continues reading beyond any reference, including one returned by a spill, a function, parentheses or a range operator. The `lookup-own-held` set (9 cases, predicted) places the `LOOKUP` next to the cells it may read: next to a spilled column, and in a row beyond what it may read, both versions of Excel and the engine agree (5); where the `LOOKUP` lies among the cells it may read but does not, the engine, which counts them all as its references, returns `#CYCLE!` and Excel calculates it (4, a known difference).

The `sortby-one-held` set (19 cases, predicted) puts a by-array with a single value into `SORTBY` alongside others: in a column, a row, a table of two columns and a single cell, with an order omitted and with orders by position. Both versions of Excel returned the same results, all 19 as predicted: a single value fits an array of one column or one row and nothing wider, the first by-array decides between rows and columns and a later one must match it (`SORTBY(A1:A6,B1:B6,1,5,1)` and `SORTBY(A1:A6,5,1,B1:B6,1)` are `#VALUE!`), and an error given as a by-array is the result.

The shared collector and array helpers were also compared with the frozen build `69b4d1f` in both execution modes and locales: 2,600 complete results matched in values, issues and both hashes, including edits, entire-column fills, row/column selection, legacy arrays and conditional aggregates. Across 672 limit checks, the result or the cell-limit error also matched at limits of 4, 20 and 100 values. These used local builds and the saved Excel fixtures, without a live Excel run.

On Node 26.7, 2026-10-09, seven alternating measured pairs after two warmup pairs (ten calls per sample) gave these medians for arrays of 34,000 elements. MAXA and AVERAGEA used mixed numbers, text and booleans; FILTER kept every third row; CHOOSECOLS selected the same column three times.

| Call | Before | Shared implementation |
|---|---:|---:|
| SUM | 0.332 ms | 0.347 ms |
| MAXA | 0.297 ms | 0.253 ms |
| AVERAGEA | 0.251 ms | 0.272 ms |
| FILTER | 0.295 ms | 0.248 ms |
| SORT | 3.564 ms | 3.429 ms |
| CHOOSECOLS | 1.064 ms | 0.940 ms |

The SUM and AVERAGEA microbenchmarks retain a small overhead. The collector stays local to the argument handler: moving it to a module-level function slowed mixed-array coercion substantially in the trial. V8's inlining trace showed the original per-element closure being inlined, while the module-level collector remained a separate function.

Five alternating pairs of `synthBook({ seed: 1, rows: 34000 })`, with closures and a fixed clock and seed, gave 1,561/1,547 ms for a full calculation and 3.71/3.53 ms for edit-A p95 (before/after). This workload showed no overall regression from the shared helpers.

Each set's predictions (`bench/coverage/entry/<set>.predicted.json`) were committed before Excel ran it, and the misses became rules. The engine now matches Excel for Windows on 1,812 of the 1,983 cases of the object-model sets, and the Mac keyboard on 232 of 236; the other cases are the known differences below, pinned in `test/entry-known.ts`.

Values are compared exactly, since the saved file stores every digit. `typed-pct-held` types percentages with decimals where moving the decimal point and dividing by 100 give different numbers (`1.1%`, `0.7%`, `1.255%`, `99.9%`, with a sign, parentheses, a leading `%`, digit groups and an exponent), along with fractions and plain decimals; each cell's value is also read through the object model (`value` on the Mac, `Value2` on Windows), which equals the number the file stores in every case. Both versions of Excel stored every decimal percentage as its decimal text represents it; the misses were `$1.1%`, which Excel en-US keeps as text, and the object model's sign difference.

Excel for Windows and Excel for Mac respond identically, except where their own built-in codes differ: the Mac's en-US short date is `m/d/yy` and its ru-RU short time `hh:mm`, so it keeps the codes `m/d/yyyy` (en-US) and `h:mm` (ru-RU) as custom formats of the workbook, where Windows treats them as formats 14 and 20. The engine follows Windows.

`test/structure-geometry.test.ts` checks that every kind of operation puts the cells where its `mapCell` says: each cell it keeps is at the address `mapCell` returns and nowhere else, a cell it removes is nowhere else, and the reverse mapping takes each cell back to where it came from; `test/session-geometry.test.ts` checks `moved` and `mapCell` of a filtered deletion and of a deleted table, done, undone and redone in every kind of session, and `null` for a sheet `mapCell` does not know. The seeded undo sessions (`test/session-undo-fuzz.test.ts`) keep a host's screen, shifted by `mapCell` and given the changes, equal to the session's values.

`test/copy-formula.test.ts` checks `copyFormula` against `copyRange` on every copy of the structure sets and the table sets: each formula of the source at each position where the copy pastes it, 317 and 8 of them.

`npx tsx bench/coverage/run.ts struct <set>` applies each case's operation to its workbook in Excel through AppleScript and stores what every sheet displays in `A1:Z60`, along with the defined names, in `test/excel/struct/<set>.json`. For workbooks with styles, it also reads the formatting of `A1:J24`: the bold, fill color and number format of each cell, widths and heights that are not standard, and the merged areas. `test/structure-excel.test.ts` compares `editStructure` with the stored results without Excel.

The formatting read also lists the hidden rows and columns. The `hidden` set writes its filtered workbook with an AutoFilter and its criteria, and runs its fills through Excel's Fill Down and fill handle as well as through copy and paste.

All cases match except the two known differences below. Of the predicted cases, `checks` matched 21 of 26, `styles-checks` 17 of 18, and `zero-held` 8 of 8 (Excel for Windows too); `names-held` 11 of 17 and `name-values-held` 12 of 17: deleting the line of a name's `$` bound makes the name `#REF!` in Excel, where the engine had shrunk it as a range in a cell, and a deleted sheet's `S!loc` becomes `'book.xlsx'!loc` (known); the misses revealed two wrong rules and a conversion error in the comparison itself, all fixed.

Not checked against Excel: a move that does not fit (it is rejected like a copy), most moves to another sheet, fonts other than bold, borders and alignment (they move with the style index). For merging: borders, fonts other than bold, the vertical alignment, and the notes, hyperlinks and `meta` of the cells a merge clears (here they keep them).

Copies were performed through AppleScript's `copy range` with a destination, which is Excel's `Range.Copy`. On a filtered sheet it pasted values. Copying and pasting in Excel's window was not tested.

Hidden sheets were tested by the `hidden` step in Excel for Mac and for Windows (`npx tsx bench/coverage/run.ts hidden <set>`, `bench/windows/run.ts hidden <set>`, `test/hidden-sheets-excel.test.ts`): sheets hidden and unhidden through the object model (`Visible`), renamed, deleted, inserted and moved next to hidden ones, with references across sheets spanning them. Each set's results were predicted before Excel ran it: `sheets-held` held in 25 of 29 cases, the misses being the very hidden sheet that neither version of Excel deletes or moves, and a sheet moved before a hidden one, which ended up after it; `sheets-held-2` in 6 of 11, the misses being moves past hidden sheets with no visible sheet after them, and ends of references across sheets that moved without passing the other end; and `sheets-held-3` in 10 of 10. Both versions of Excel responded identically ([Hidden sheets](#hidden-sheets)).

Merging cells was tested in Excel for Windows (`npx tsx bench/windows/run.ts struct <set>`: `Range.Merge`, `Range.UnMerge`, and Merge & Center as `Merge` with the alignment centered, with alerts off), whose results are in `test/excel/win/struct/` and compared by `test/structure-win.test.ts`; Excel for Mac was not tested. The formatting read there also includes the horizontal alignment. A case can perform an operation before its own (`before`): cells merged and split again display the formatting the merge gave them, and a table is created over the cells first (`ListObjects.Add`). Each set was predicted before Excel ran it. `merge` (28 cases) held in 20: an empty top-left cell takes the area's first value (6 cases, where the prediction kept it empty), and Excel writes a merged area of entire rows as `20:21` (2, the same area). `merge-held` (18) held in 10: the value moves as cut and paste moves it, with the references to it and its formatting (8). `merge-third-held` (12) held in all 12, and `merge-top-held` (3), references to the empty top-left cell, in all 3. `test/merge-cells.test.ts` checks that a session produces the same workbook as `editStructure` on every case, with and without rebuilding the state, and undoes and redoes it in one step in every kind of session.

The fill handle was tested in Excel for Windows by the same step (`Range.AutoFill` over the range `to`, with type `xlFillDefault`, `xlFillSeries` or `xlFillCopy`), in en-US, with three sets, each predicted before Excel ran it. `fill` (46 cases) held in 38: dates at the ends of months continue by months, `Q1` continues by quarters, `1st` by ordinals, a number before text continues, and a lone number next to text increases by 1; three more cases differed only in the comparison, which now writes the engine's numbers with Excel's 15 digits. `fill-held` (45) held in 37: an empty cell does not end a run, dates and text without a constant step are copied, months continue only from the same day of the month or from month ends, a number at the start needs a space after it and takes precedence over one at the end, ordinals use lowercase suffixes, and a lone number is copied only when the source contains only numbers. `fill-third-held` (31) held in 28: a date next to a lone number makes it continue, steps are compared to 15 digits (`9:00, 10:00, 11:00` continue by the hour), and a number at the start loses its leading zeros (`007 x`, `8 x`). After those corrections, all 122 cases match; no fourth set was run. Over hidden rows, the `hidden` set showed Excel's fill handle (as `copyRange` cases through `Range.AutoFill`) filling rows hidden manually and by a filter alike, on the Mac and on Windows, whereas the engine's fills had skipped the rows hidden by a filter; `fill-hidden-held` (16 cases on the same workbooks: text and a formula, numbers and texts by default and as copies, a fill up, sources that contain hidden rows) was predicted with the fill's copies taking the whole source over every row, and all 16 held. `test/fill-range.test.ts` checks that a session produces the same workbook as `editStructure` on every case, undoes and redoes it in one step in every kind of session, and keeps dates given as text.

### Tables

From [Tables](tables.md).

`npx tsx bench/coverage/run.ts tables <set>` writes each case's workbook with `writeXlsx`, opens it in Excel, performs the case's steps (typed cells, structure and table operations) through AppleScript, and reads the values of the case's cells, their formulas as Excel displays them (in Russian too, for a ru-RU set), and the tables of every sheet. `test/tables-excel.test.ts` replays the steps in a session and compares the rejected steps, the tables, the values and the formulas, read as stored text and as `toLocal` displays them.

| set | cases | what |
|---|---|---|
| `refs` | 8 | every part of a table, the formula's row from everywhere, references without a table name inside one, no header row, a totals row, escapes, names, arrays |
| `refs-held` | 5 | predicted before Excel calculated them: a table away from A1, the totals row, more escapes, names, arrays next to tables |
| `ops` | 51 | rows and columns inserted and deleted around tables, renames, conversions, deletions, sheets, header cells, copies and moves |
| `ops-held` | 18 | predicted before Excel performed them: inserts next to another table, a table emptied, pastes over header rows, renames Excel rejects |
| `locale` (ru-RU) | 4 | the Russian specifiers displayed and typed, a totals row, the names of new columns |
| `more` | 5 | entire tables copied and moved, cells typed next to and into a table |
| `names-held` | 17 | predicted before Excel calculated them: defined names in letters of any script, tables renamed to Cyrillic names and to names Excel rejects |
| `names-ru-held` (ru-RU) | 8 | predicted before Excel calculated them: the same names in formulas typed in Russian |
| `names-more-held` | 12 | predicted before Excel performed them: defined names added through Excel's object model where its rules reject them, files with `?` and `\` in a name |
| `names-ru-more-held` (ru-RU) | 10 | predicted before Excel performed them: the same in ru-RU, and files with the name `ИСТИНА` |

| `names-ru-tables-held` (ru-RU) | 3 | predicted before Excel performed them: tables renamed `ИСТИНА`, `ложь` and `TRUE` |
| `delete-held` | 13 | predicted before Excel performed them: rows and columns deleted that remove one table entirely and part of another, or both entirely |
| `headers-ru-held` (ru-RU) | 13 | predicted before Excel performed them: numbers, dates and text typed into a header cell, and the formulas over the column in English and in Russian |
| `paste-names-held` | 5 | predicted before Excel performed them: a table's cells pasted onto a destination that is not a multiple of them, a row inserted where a calculated column's formula differs from its cells' formulas, defined names shaped like cells |

The predicted sets came out as predicted on 81 of 81 cells (`refs-held`), 424 of 433 (`ops-held`: two pastes over header cells, which Excel renames, and a conversion seen through a name were found there and fixed), and 69 of 69 (`locale`); `delete-held` on 5 of 13 cases, as Excel for Mac and Excel for Windows both reject a deletion that removes one table entirely and part of another, which the engine accepted (fixed); `headers-ru-held` on 3 of 13 cases: the column's name and the stored formulas on 10, where a header cell's own number format (`0.00`, the short date) names the column as it displays the number, while the engine named it as General would (fixed), and Excel parsed typed text as a date (a known difference); and `toLocal` in ru-RU split a column named `1,5` at its comma and put it in brackets after `@` (fixed). The name sets came out as predicted on 34 of 54 cases in Excel for Mac; [Defined names](names.md) lists the misses and what was fixed. `paste-names-held` came out as predicted on 1 of 5 cases in both versions of Excel: a copy of formulas onto a destination that is not a multiple of them also took the destination's other cells, and a formula there in another table's calculated column got the copied table's name (fixed); formulas pasted into part of a calculated column fill the entire column in Excel (known); defined names beyond the sheet (`XFE1`, `A0`) are names (fixed); and a row inserted where a calculated column's formula differs from its cells' formulas gets the column's formula, as predicted.

`test/tables-text.test.ts` displays formulas of a table's cell with `toLocal` and the table, in en-US and ru-RU, parses them back with `toInvariant`, and checks the typed text with `validateLocalFormula`, each with the table, and both produce the stored text again; the canonical text `validateFormula` returns with the table is the one `compute` stores for the cell.

The xlsx round trip (`run.ts xlsx roundtrip`) sends the 29 distinct workbooks of the sets `refs`, `refs-held`, `ops` and `ops-held`: Excel opens each file `writeXlsx` writes and saves it, the files it saved read back to the workbooks that were written, and the values Excel stored in them equal the engine's.
